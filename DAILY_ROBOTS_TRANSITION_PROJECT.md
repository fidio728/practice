# Daily robots.txt Transition Pipeline — Briefing

Hand-off doc for a fresh chat window. Self-contained: a new agent should be
able to start cold from this file. Author: assistant + user, 2026-05-03.

---

## Research goal

For each `(firm host, AI bot)` pair, find the **first observed `Disallow`
event** with day-level (Wayback timestamp-level) precision — and explicitly
quantify uncertainty around it.

Output schema (one row per `(host, bot)` pair):

```
host
bot                              # GPTBot, ClaudeBot, CCBot, ...
first_observed_blocked_ts        # 14-digit Wayback ts of first capture where bot is Disallow'd
                                  #   AND prev interpretable capture had bot allowed
last_unblocked_ts                # 14-digit ts of the last interpretable capture
                                  #   immediately before first_observed_blocked_ts
                                  #   that was non-blocking for this bot
interval_days                    # (first_blocked - last_unblocked) in days
ever_blocked                     # bool — false means we never saw blocked status
n_captures_total                 # how many CDX captures we have for this host
n_interpretable_total            # how many were 200/404/410 (not 3xx/5xx/etc.)
```

**Important naming convention** (per user 2026-05-03 design discussion):
this is `first_observed_blocked` — NOT a real "the day the firm decided
to block GPTBot." Real change day is unobservable. Wayback only shows us
that `block was already in effect by some capture`. The `interval_days`
column quantifies uncertainty: a high-precision event is one with
`interval_days <= 7` or `<= 14`. Event-study filters on this.

## Four design constraints (user-stated, must follow)

1. **Fetch by unique digest, NOT (host, digest), NOT per-capture.**
   Wayback's digest is content SHA-1. Same digest = same robots body, even
   across hosts. CDX has 25.9M captures → 425,329 unique digests → only
   99,745 of those have status=200 (= parseable). So the actual fetch queue
   is ~99k, not millions.

2. **`workers × rate-limit` is misleading.** The fetcher's `throttle()`
   is process-global lock, not per-worker. So `workers=10 rate=0.5s` =
   2 req/s/machine, not 20. With 16 machines → 32 req/s globally.
   workers > 4-6 is wasted unless rate is much lower. Round 2 of Step 6.5
   confirmed this empirically.

3. **Status semantics must match Step 2's main-line tier definition:**
   - `200` (or revisit-resolved 200) → parse robots → bot policy
   - `404` / `410` → "no robots policy" = allow-all
   - `3xx` / `403` / `5xx` / unresolved / `429` / `400` / `202` / etc. → **uninterpretable**
   - no CDX capture in window → **gap**
   Don't let daily timeline drift from this; main results stay comparable.

4. **Interval censoring is mandatory.** The "first observed blocked" is
   only as precise as the gap between captures. Many firms have monthly
   captures only — interval might be 30 days. Filter to
   `interval_days <= 7` (or `<= 14`) for the event-study sub-sample.
   Don't claim anything stronger.

5. **Thread-local `requests.Session` per worker is critical** (carried
   over from Step 6.5 round 2 lesson). Per-fetch `Session()` + `close()`
   was a major contributor to ConnectionError storms. Reuse the TCP/TLS
   handshake. See `06_5_collect_sitemap_paths_monthly.py`'s `get_session()`
   helper for the pattern.

## Pipeline to build

### Step A. Build digest → robots-body cache (fetch ~99,745 digests)

**Inputs:** `cdx_unique_digest_index.jsonl`, filtered to `sample_status == "200"`.

**Per item:** GET `https://web.archive.org/web/{sample_ts}id_/{sample_url}`
→ save raw body. NO sitemap recursion. NO XML parsing. Just save bytes.

**Output:** `digest_robots_cache.jsonl` with rows:
```
digest, sample_ts, http_status, content_sha1, content_text (or null), error
```

**Deployment:** 16 GCP/DO machines (same hosts used in Step 6.5 rounds).
Push input + script. Use thread-local session pattern. Suggested:
- `--workers 4` (or 6, but rate-limit dominates)
- `--rate-limit 0.5` (test) / `0.7` (safer)
- `--num-shards 16`

Throughput estimate: 16 machines × ~2 req/s = 32 req/s → **99,745 / 32 ≈
52 min** if no Wayback throttle reaction. Could be 60-90 min if minor
throttle. Should NOT spike to round-1-style 50% NET because robots files
are tiny (1-5 KB) and request volume is far below sitemap stage.

**Script to write (suggested name `06_robots_daily_fetch_digests.py`):**
- argparse: `--shard / --num-shards / --data-dir / --workers / --rate-limit / --input-digest-jsonl`
- reuse helpers from `06_5_collect_sitemap_paths_monthly.py`:
  - `wayback_url`, `fetch_content_once`, `throttle`, `get_session`
- output filename: `digest_robots_cache_m{shard}.jsonl` per machine
- resume logic: skip digests already in output

### Step B. Parse digest cache → bot policy table

**Local script** (no network). For each digest in the cache:

```python
from urllib import robotparser  # or roll your own — see below

# For each major bot:
for bot in ["GPTBot", "ClaudeBot", "Claude-Web", "CCBot", "Anthropic-AI",
            "Google-Extended", "Applebot-Extended", "PerplexityBot",
            "Bytespider", "Amazonbot", ...]:
    blocked = robots_disallows(content, bot, path="/")
```

**WARNING about robotparser:** Python stdlib `urllib.robotparser` has
known correctness gaps for `User-agent` matching with case sensitivity
and group inheritance. For this project, write a focused parser that:

1. Tokenizes by `User-agent:` group blocks
2. For each query bot, finds matching groups (exact match preferred,
   `*` fallback). Match is case-insensitive on UA name.
3. Within matching group, applies `Disallow:` and `Allow:` rules in
   order; checks if path `/` is reachable.
4. Returns `True` (blocked) if `Disallow: /` matches before any `Allow: /`.

This must MATCH whatever Step 2's main-line robots parser does. Re-use
that code if possible. (Find it under `bot_paper/panel_construction/`.)

**Output:** `digest_bot_policy.csv` keyed by `digest`:
```
digest, n_groups_in_robots, GPTBot_blocked, ClaudeBot_blocked, ...,
parse_error
```

Bots list comes from your existing main-line bot inventory.

### Step C. Reconstruct timeline → first-block events

**Inputs:**
- `digest_bot_policy.csv` (from B)
- `cdx_snapshots*.jsonl` (raw CDX with all timestamps)

**For each (host, bot) pair:**

1. Build the host's full timeline: list of `(timestamp, status, digest)`
   ordered by timestamp.
2. Map each capture to bot status using Step 2 semantics:
   - `200` + digest in policy table → blocked or allowed per parsed policy
   - `404` / `410` → allowed (no robots policy ⇒ allow-all)
   - other → `uninterpretable` (skip in transition detection but track for
     `n_interpretable_total` accounting)
3. Find the first `(ts_blocked)` such that:
   - status at `ts_blocked` is interpretable AND bot=blocked
   - the most recent earlier interpretable capture has bot=allowed
   This is `first_observed_blocked_ts`. The "most recent earlier
   interpretable capture" gives `last_unblocked_ts`.
4. If no such transition (always blocked, never blocked, or no
   interpretable captures), emit a row with `ever_blocked=False/True` and
   nulls for the timestamps as appropriate.

**Output:** `daily_first_block_events.csv` per the schema at the top.

### Step D. Sub-sample for event study

```python
df = pd.read_csv("daily_first_block_events.csv")
df_high_precision = df[df["interval_days"] <= 14]   # or <= 7
```

Use `df_high_precision` for short-event-study work. Cite censoring level.

## Things NOT to do

- **Don't call the result "the day the firm blocked the bot."** It's
  "first observed blocked event with X-day precision."
- **Don't fetch every CDX capture.** Fetch by digest, join back. The whole
  motivation of the digest-based design is to NOT do per-capture fetches.
- **Don't fetch digests with status != 200.** Their bot policy is
  determined by Step 2 status mapping, not by content. Fetching their
  Wayback URLs would just download a 404 error page or a redirect HTML.
- **Don't mix this with Step 6.5 outputs.** Step 6.5 is sitemap path
  collection; this pipeline is robots.txt content. Different inputs,
  different outputs, different downstream uses.
- **Don't skip thread-local session.** The Step 6.5 round 2 confirmed
  this is the difference between 50% NET and 1% NET. Same lesson here.

1. Read this whole doc.
2. Confirm `cdx_unique_digest_index.jsonl` exists on E:.
3. Filter to `sample_status == "200"` (~99,745 rows). Save as
   `cdx_digest_to_fetch.jsonl`.
4. Write `06_robots_daily_fetch_digests.py` modeled on the Step 6.5
   fetcher but stripped of sitemap parsing — only HTTP GET + body save.
5. Push script + queue to 16 hosts. Launch with shard splitting.
6. Wait 60-90 min for fetch.
7. Pull all `digest_robots_cache_m{N}.jsonl`, merge to local.
8. Locally parse each digest's body for each bot's `Disallow` status.
9. Reconstruct timelines from CDX + parsed bot policy.
10. Output `daily_first_block_events.csv` with `interval_days`.
11. User does event-study filtering on `interval_days <= 14`.

Don't go past step 5 in one shot — pause for user approval after step 4
(script ready to deploy) and after step 7 (cache pulled, parser ready).
